This is a federated decision-support platform for a port. Several separate models — throughput, berth use, fuel cost, emissions — are linked together so that when one assumption changes, every model that depends on it re-runs automatically, and you can see exactly what moved and why.

Baseline→ Excel assumptions→ Validate→ Commit→ Detect change→ Propagate→ KPI impact→ Why→ Provenance→ Execution→ Governance
The numbers here are synthetic. The port models are simple, clearly labelled arithmetic written to demonstrate the platform — they are not calibrated real-world port figures, and they are not anyone's proprietary modelling. Everything you see was computed by this application from the assumptions it holds.

1 · What this system does

Most planning work lives in disconnected spreadsheets and models. Change a fuel price in one place and somebody has to remember to update four other things. This platform makes those links explicit and machine-enforced:

  • Models are registered, each with a declared set of inputs and outputs.
  • Datasets connect them. One model's output is another's input, and every dataset has a contract — field names, types, units, allowed ranges.
  • Changes cascade. When a value changes, the platform works out every model downstream of it and re-runs them in dependency order.
  • Everything is recorded. Each run, each result, and each value's origin is stored, so any number on screen can be traced back to where it came from.

2 · Baseline and scenario

The baseline is the agreed truth

A baseline is a named, executed snapshot of the port as everyone has agreed to describe it — the current assumptions, and the results every model produced from them. The shipped baseline is Current operations. It is the thing everything else is compared against.

A scenario is a question about the baseline

A scenario asks “what if one thing were different?”. It starts from the baseline and applies one or more overrides — a single assumption given a different value. The shipped scenario is Higher bunker price, which overrides the in-port bunker price and leaves everything else alone.

Running a scenario never changes the baseline. Scenario results are held separately and are never automatically approved for sharing.

4 · How to change assumptions with Excel

  1. Download the workbook

    In the workspace, open Excel assumptions and download the .xlsx. It is pre-filled with the values the platform holds right now, so the only difference after you edit it is the change you made.

  2. Edit one number

    Change a value in the Value column and save as .xlsx. Do not insert or delete rows — the platform reads fixed cell addresses (Assumptions!B2 is the bunker price, and so on). The workbook's “How to use” sheet lists the full cell map.

  3. Upload and validate

    Choose the file and press Validate workbook. This is a dry run: the platform reads every mapped cell, compares it to the current value, and runs the same contract checks the real ingestion runs — but it writes nothing, records no ingestion and re-runs no models.

  4. Review what would change

    You get a row per mapped cell showing the source cell, the field, its unit, the current value, the value in your workbook, and whether it is valid. Changed rows are highlighted. If something is invalid you are told which cell and why, before anything happens.

  5. Commit the ingestion

    Press Commit ingestion. Now the values are written. The platform records an ingestion with the workbook's SHA-256 fingerprint and a timestamp, detects which fields actually changed, and raises a change event.

  6. Watch it propagate

    The change event triggers every model downstream of the changed dataset, in dependency order, as one graph run. The workspace then shows you the chain that just happened — workbook → ingestion → change → propagation → results.

What happens on the second upload

Upload the same file again and the platform reports unchanged: the ingestion is still recorded, but no change event is raised and no model re-runs. Change one number and only that field is listed as changed. Change detection is on the values, not on the file.

What the Excel connector will not do

  • Formulas are never evaluated. The connector reads the value Excel cached when the file was last saved. A formula cell that has never been saved by Excel is rejected with a message telling you to re-save it — it is not guessed at.
  • Macros and VBA are never executed. Workbooks open read-only with macro support disabled.
  • Only the mapped cells are read. Other sheets, formatting, charts and extra rows are ignored entirely.
  • Your file is never modified and never stored. Only its hash and the mapped values are kept.
  • Only .xlsx is accepted — not .xls, .xlsm or .csv — up to 5 MB.

5 · Where the results appear, and why they moved

  • Decision overview — the headline KPIs, baseline against scenario.
  • Comparison — every metric with its baseline value, scenario value, absolute change and percentage change.
  • Impact & why — the chain of reasoning: which assumption changed, which model consumed it, what that model produced, and which KPI it landed in. This is the answer to “why did this number move?”.
  • Sources & provenance — where each value came from: which workbook, which fingerprint, which ingestion, which change event.
  • Execution — the actual runs: which models executed, in what order, how long they took, and whether any step failed.
  • Governance — who the federation participants are, what each has approved for external exposure, and which fields are therefore visible outside. Approved does not mean visible: an approval held by an inactive participant, or a revoked one, is excluded.

6 · What this project actually implements

This project is built as an open replication of the kind of capability the Sentient Ports / Sentient Hubs material describes publicly. It is an independent implementation: no proprietary code, private algorithms, branding or undocumented internals were used. Being straight about the gap matters more than the claim:

CapabilityStatus hereWhat that means
Linking models into one governed solutionImplemented Registry, contracts, dependency graph, orchestrated runs.
Cascading impact across modelsImplemented Change events propagate in dependency order.
Scenario modellingImplemented Baselines, overrides, isolated scenario runs, comparison.
Excel as a data sourceImplemented Template, dry-run validation, commit, provenance, propagation.
Provenance and lineageImplemented Every result traces to its inputs and to its source workbook.
Data-sharing governanceSynthetic The approval and exposure model is real and enforced; the participants and agreements shipped with it are synthetic demo records, not real agreements.
Cross-domain impactsPartial Operational, economic and environmental domains only. No natural or social domain models.
Port domain logicIllustrative Deliberately simple arithmetic, not calibrated port modelling.
Other data connectorsNot implemented Excel is the only connector. No database, API or sensor connectors.
Live sensor feeds / real-time viewNot implemented There is no telemetry ingestion. Nothing here is live data.
Operational optimizationNot implemented No optimiser or solver exists. The platform evaluates the assumptions you give it; it does not search for better ones.
Dynamic master planningNot implemented Scenarios are single-point. There is no multi-horizon time-phased planning.

7 · Running this as a shared service

By default this runs on one machine with a local SQLite file, which is fine for trying it out but means nobody else can reach it and the data lives on that laptop.

The repository ships a container image and a PostgreSQL configuration so it can run as a shared service that survives a laptop being closed. The exact steps — including the one manual step that needs a hosting account — are in DEPLOYMENT.md.
